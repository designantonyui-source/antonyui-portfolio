Architecting a multi-brand design system without losing your mind

How to structure shared components, token inheritance, and multi-theme matrices across different products without duplicating libraries or building 50-variant Frankenstein components.

When an organisation operates more than one product or brand — through mergers and acquisitions, white-label partner platforms, or a consumer vs. enterprise product split — leadership will inevitably say:

"Why don't we just build one shared design system for all our brands?"

On an executive roadmap slide, it looks like pure efficiency. One shared codebase, halved frontend development costs, unified accessibility compliance, and instant cross-pollination of UX improvements. But if you have ever tried to execute this naively, you know that multi-brand systems are where good intentions go to die.

Without a rigorous architectural boundary, multi-brand design systems fail in one of two catastrophic ways.

The two false summits

1. The Fork (Copy-Paste Architecture)

Brand B needs a dark brutalist aesthetic with 0px corner radii and orange accents; Brand A has soft 12px rounded corners and purple primary buttons. Under pressure to ship Brand B's MVP in six weeks, the team copies the entire Figma library into a new file (Brand-B-Core.fig) and clones the Git repository into @company/brand-b-ui.

The short-term velocity feels great. Then reality hits:

  • You no longer have a multi-brand system. You have two single-brand systems and double the maintenance overhead.
  • Six months later, an accessibility audit finds a severe keyboard focus-trap bug in the modal dialog on Brand A. An engineer fixes it. Nobody has time to backport the commit to Brand B's repository.
  • Brand B falls behind, bugs multiply, and the company ends up paying two full design-engineering squads to maintain parallel components that do the exact same mechanical job.

2. The Megacomponent (Variant Hell)

Determined not to duplicate files, another team keeps everything in one shared library. But because they lack a decoupled token architecture, they bake brand differences directly into component props and Figma variants:

<Button 
  variant="primary" 
  isBrandB={true} 
  cornerStyle="brutalist-sharp" 
  elevation="none" 
  hasAccentBorder={true}
/>

In Figma, a single Button component now has 48 variant combinations, four boolean toggles, and three variant properties just to handle different logos, border styles, and shadows. Designers get lost selecting properties, Figma files lag and crash browser tabs, and frontend production bundles ship dead CSS for brands they aren't even running.

The core pattern: Headless Anatomy vs. Token Skin

The only sustainable way to build multi-brand systems is enforcing an unbreachable wall between Component Anatomy (the invariant mechanical core) and Token Skin (the brand-specific styling layer).

1. What belongs in the Invariant Anatomy:

Take a complex component like a Date Range Picker or a Modal Dialog. Mechanically, how it works does not care whether it is sitting in a consumer solar energy shop (priWatt) or an enterprise fintech payment gateway (PGWay):

  • Keyboard traversal (arrow keys, Tab, Shift+Tab, Escape to close).
  • ARIA roles (role="dialog", aria-modal="true", aria-describedby).
  • Focus management (trapping focus inside the modal, restoring focus to the trigger on dismiss).
  • Hit target boundaries (minimum 44×44px touch targets).

In Figma, you maintain one master component. In code, engineering writes one component package.

2. What belongs in the Token Skin:

Visual styling is never hardcoded inside the component. Every visual attribute is an unresolved reference to a semantic design token:

  • Surface background & backdrop blur
  • Border color, width, and radius
  • Typography family, weight, and line-height scale
  • Shadow elevation coordinates
  • Internal padding and gutter spacing

The five production battlegrounds

Separating anatomy from skin sounds simple in theory. In production, five major friction points will test your architecture:

Battleground 1: Typography geometry & vertical rhythm

This is where multi-brand systems silently break. Brand A uses a modern geometric sans (Inter) with tall x-heights; Brand B uses an editorial serif (Playfair Display) or a tabular monospace font with wide proportions.

If your button component defines fixed heights (e.g. height: 40px; line-height: 20px;), changing the font family causes text clipping, unaligned baseline centers, or awkward button padding because different typefaces have radically different ascender, descender, and cap-height metrics.

The architectural solution:

  1. Never set explicit fixed heights on buttons, inputs, or badges. Let components size organically using padding-block and padding-inline.
  2. Tokenize typography as cohesive functional text styles rather than standalone font sizes. Instead of exposing font-size: 16px, expose type.interactive.label, which bundles font family, size, line-height, and letter-spacing tuned per brand.
  3. Where modern browser support permits, leverage CSS leading-trim (or text-box-trim) to strip font-metric white space above and below glyphs, guaranteeing pixel-perfect optical centering across any typeface.

Battleground 2: Corner radius polarization (Brutalist vs. Pill)

What happens when Brand A requires 0px sharp corners, but Brand B requires 9999px full pill buttons? If your button component uses a primitive token like border-radius: var(--radius-4), setting --radius-4: 9999px in Brand B will fix buttons, but it will turn your table cards and modal dialogs into monstrous capsules.

The solution: Contextual semantic radius tokens

/* Global Primitives */
radius.0:    0px
radius.4:    4px
radius.8:    8px
radius.full: 9999px

/* Semantic Mappings per Brand */
/* BRAND A (Enterprise Data / Clean) */
radius.interactive.action:  {radius.4}
radius.surface.card:        {radius.8}
radius.surface.overlay:     {radius.8}

/* BRAND B (Modern Neo-Consumer) */
radius.interactive.action:  {radius.full}
radius.surface.card:        {radius.16}
radius.surface.overlay:     {radius.24}

Now, changing radius.interactive.action to radius.full transforms buttons without touching container cards.

Battleground 3: Information density (Compact vs. Comfortable)

In fintech applications (like the PGWay payment terminal), operators need high data density: 40 rows per table, 32px row heights, compact font sizes. In consumer products, generous whitespace (48px-56px rows) is essential for readability and thumb-friendly touch targets.

Do not create separate "Compact" and "Regular" component variants in Figma. Introduce a Density Modifier Token:

/* Spacing scales dynamically via a density multiplier */
:root {
  --density-multiplier: 1; /* Comfortable */
  --space-table-cell-y: calc(16px * var(--density-multiplier));
}

[data-density="compact"] {
  --density-multiplier: 0.625; /* 10px padding for dense data */
}

Battleground 4: The 2D matrix of Brand × Color Mode

If you support 3 brands, and each brand supports Light and Dark mode, you are managing six distinct themes. If you try to maintain six separate Figma files, you will fail.

In Figma Variables, create a two-collection architecture:

  • Collection 1: Primitives: All raw brand colors (Brand A Blues, Brand B Oranges, Neutral grays).
  • Collection 2: Semantic System: Set up modes as a 2D matrix (Brand A Light, Brand A Dark, Brand B Light, Brand B Dark).

In CSS, themes are scoped via container classes or data attributes:

<!-- Brand A in Dark Mode -->
<body class="theme-brand-a" data-mode="dark">
  <!-- All child components automatically inherit Brand A Dark tokens -->
</body>

Battleground 5: Iconography sets & brand signatures

Brand A uses 1.5px linear outline icons; Brand B uses 2px filled duotone icons. If an SVG icon is hardcoded inside an alert or button component, swapping the brand theme produces a jarring visual clash.

We treat icons as headless slot components:

  • The component exposes an icon slot rather than a hardcoded graphic.
  • Icons are authored to inherit currentColor for strokes and fills.
  • Optical sizing is tokenized (icon.size.sm = 16px, icon.size.md = 20px).

Governance: The "Rule of Two"

The ultimate failure point of a multi-brand design system is rarely technical — it is organizational. Product managers under sprint deadlines will constantly pressure designers to add brand-specific one-offs to the core component library.

To defend system integrity, we established the Rule of Two:

A component variant or style override is never admitted into the Core System for a single brand. It must exist in that brand's local product file until a second brand demonstrates a verified, production-backed need for the same pattern.

When a pattern graduates to Core, the design systems team absorbs ownership, writes automated visual regression tests across all brand themes, and documents the handoff contract.

Automated verification: protecting contrast at scale

When someone changes a primary action token for Brand A, how do you know they didn't accidentally break WCAG contrast compliance in Brand B or Dark Mode? You cannot test 500 screens manually.

We solved this in CI/CD:

  • Automated Contrast Checkers: A Node script runs on every token PR, calculating APCA / WCAG 2.2 contrast ratios between all registered text/surface pairs across every theme mode. If color.action.primary.text drops below 4.5:1 on color.action.primary.bg in any theme, the pull request is blocked.
  • Visual Regression Matrix: Using Playwright and Storybook, every component is screenshotted across all six brand-mode configurations on every push. Any visual drift is flagged immediately in GitHub diffs.

Conclusion

Building a multi-brand design system isn't about making everything look identical. It is about building an industrial-grade engine where mechanics, accessibility, and interaction logic are solved once — leaving design teams free to express true brand distinctiveness through the token layer.
