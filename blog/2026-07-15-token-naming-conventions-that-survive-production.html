The token naming conventions that actually survive production

Why most design token taxonomies collapse the moment dark mode, multi-brand themes, or deadline pressure arrive — and the 3-tier grammar that holds up across Figma, CSS, and mobile.

Every designer who gets excited about design tokens goes through the exact same arc. You discover Token Studio or Figma Variables, read twenty articles on taxonomy, feel like a librarian of pure digital order, and create an eight-layer naming scheme:

sys.color.surface.interactive.primary.hover.on-light.default

You export the JSON, deliver a proud presentation to engineering, and hand off the first batch of screens. Three sprints later, you inspect a pull request and discover the frontend developer has hardcoded #1A1A1A. Why? Because when building a complex payment table under a Friday release deadline, nobody has the patience to parse eight layers of abstract adjectives to decide between surface-container-high and surface-container-highest.

If your token system is too clever for an engineer to guess without opening documentation, it will fail in production. That is not an engineering discipline problem — it is an architecture failure on our part.

Why token systems break: three real-world post-mortems

Before designing a naming schema, it helps to study the three exact failure modes that destroy token initiatives inside fast-moving product teams:

1. The Material Design 3 copycat trap

Google's Material 3 token architecture is brilliant for an operating system powering thousands of disparate apps on Android. But when a 15-person product team copies terms like on-surface-variant, surface-container-low, and outline-variant into a bespoke B2B SaaS tool, disaster strikes. Designers don't intuitively remember which layer is "low" versus "lowest", so they guess randomly. Within two months, three different designers use three different background tokens for identical card components.

2. The visual description trap

When teams start with a brand book, tokens get named after how they look: color-blue-500, text-grey-dark, or border-light. Everything seems fine until the company asks for Dark Mode. In dark mode, dark grey text must invert to white, and light grey borders become charcoal lines. You end up with CSS like this:

[data-theme="dark"] {
  --text-grey-dark: #F5F5F7; /* Inverted! Mental breakdown for devs */
  --border-light: #2A2A2E;   /* A "light" border that is almost black */
}

Every engineer who joins the company will look at that code, shake their head, and start creating ad-hoc inline styles because the existing tokens make no sense.

3. The context explosion trap

When a designer tries to prevent accidental regressions, they often create hyper-specific tokens for every single HTML element: sidebar-header-nav-link-hover-color, table-row-selected-badge-border. You end up with 2,400 tokens, 95% of which point to the exact same blue hex code. When marketing asks to change the brand accent, you have to update forty different tokens because nobody grouped them by semantic role.

The 3-tier hierarchy that actually works

Through shipping and refactoring design systems across payment gateways (PGWay), energy commerce (priWatt), and enterprise SaaS, I have found that a strict three-tier model is the sweet spot between scalability and developer adoption: global primitives at the foundation, semantic intent in the middle, and strictly constrained component overrides at the top.

Tier 1: Global / Raw Primitives

These are your dictionary words. They describe what a value is, completely detached from where or how it is used in the interface. They should never be consumed directly in UI components.

  • Color: Use numeric step scales (e.g. 50 through 950 or 100 through 900). Numeric scales provide predictable perceptual increments when tuning accessibility contrast.
  • Spacing & Radius: Use t-shirt sizing (xs, sm, md, lg, xl) or 4px/8px modular scales (space-4, space-8, space-12, space-16).
/* Tier 1: Global definitions */
color.brand.blue.500:   #0066FF
color.neutral.50:       #F8F9FA
color.neutral.100:      #F1F3F5
color.neutral.800:      #343A40
color.neutral.900:      #212529
color.red.600:          #DC2626

space.2:                2px
space.4:                4px
space.8:                8px
space.12:               12px
space.16:               16px
space.24:               24px

radius.none:            0px
radius.sm:              4px
radius.md:              8px
radius.lg:              12px
radius.full:            9999px

Tier 2: Semantic (System / Intent) Tokens

This is the workhorse of your design system. Semantic tokens describe the intent or role of a style. They answer the question: "What functional purpose does this color, border, or spacing serve?"

Semantic tokens are where mode switching (Light vs. Dark Mode, High Contrast, Brand Theming) occurs. The component markup never changes — only the pointer resolves to a different primitive.

/* Tier 2: Semantic mappings for Light Theme */
color.surface.canvas:            {color.neutral.50}
color.surface.panel:             #FFFFFF
color.surface.danger.subtle:     #FEF2F2

color.text.default:              {color.neutral.900}
color.text.muted:                #6B7280
color.text.on-brand:             #FFFFFF
color.text.danger:               {color.red.600}

color.border.subtle:             #E5E7EB
color.border.focus:              {color.brand.blue.500}

color.action.primary.bg:         {color.brand.blue.500}
color.action.primary.bg-hover:   #0052CC
color.action.primary.text:       #FFFFFF

/* Tier 2: The exact same tokens re-mapped for Dark Theme */
[data-theme="dark"] {
  color.surface.canvas:          #0F1115
  color.surface.panel:           #181B20
  color.surface.danger.subtle:   #450A0A

  color.text.default:            #F9FAFB
  color.text.muted:              #9CA3AF
  color.text.on-brand:           #FFFFFF
  color.text.danger:             #F87171

  color.border.subtle:           #2D333B
  color.border.focus:            #3B82F6

  color.action.primary.bg:       #2563EB
  color.action.primary.bg-hover: #1D4ED8
  color.action.primary.text:     #FFFFFF
}

Tier 3: Component Tokens (The Guardrail Tier)

Component tokens alias a semantic token to an isolated component property:

btn.primary.bg:        {color.action.primary.bg}
btn.primary.bg.hover:  {color.action.primary.bg-hover}
btn.primary.text:      {color.action.primary.text}

The golden rule of component tokens: Do not create them by default. Start by building components using Tier 2 semantic tokens directly (e.g. background: var(--color-action-primary-bg)). Only introduce a Tier 3 component token if:

  1. A specific component has a unique internal sub-element (like the track of a slider or the notch of a tooltip) that would pollute the global semantic space if elevated to Tier 2.
  2. Product marketing requires overriding that exact component's appearance in white-label configurations without affecting any other interactive elements.

If you create component tokens for every single button, badge, input, and modal on day one, you will drown in 2,000 token mappings before you even ship your first feature.

The strict naming formula: grammar that scales

To make autocomplete in VS Code and Figma instant, every token name must follow a consistent, predictable left-to-right grammatical order:

[CATEGORY] ─ [CONTEXT / ELEMENT] ─ [ROLE / INTENT] ─ [STATE / MODIFIER]

Here is how this grammar breaks down across the design system:

  • Category: color, space, font, radius, elevation, motion.
  • Context / Element: surface, text, border, icon, action, layout.
  • Role / Intent: default, muted, brand, success, warning, danger, info.
  • State / Modifier: hover, active, pressed, focus, disabled, subtle.

Compare bad naming vs. production-grade naming:

❌ text-grey-dark            →  ✅ color.text.default
❌ primary-btn-blue          →  ✅ color.action.primary.bg
❌ danger-box-border         →  ✅ color.border.danger
❌ sidebar-padding-16        →  ✅ space.layout.sidebar-gutter
❌ card-shadow-big           →  ✅ elevation.overlay.modal
❌ light-mode-hover-color    →  ✅ color.action.primary.bg-hover

The contract between Figma and Code

The single greatest cause of design system decay is nomenclature divergence. If the Figma Variables panel says Action / Primary / Hover and the React codebase uses theme.colors.brandPrimaryHover, your system is already fracturing. Every sync meeting between design and engineering will waste time translating between dialects.

In our pipeline at priWatt, we established a single source of truth:

  1. Tokens are authored and maintained in Token Studio / Figma Variables using dot-notation.
  2. Tokens are committed directly to a shared GitHub repository as structured JSON.
  3. A GitHub Action runs Style Dictionary on merge, compiling the JSON into:
    • variables.css (CSS Custom Properties with kebab-case: --color-action-primary-bg)
    • tokens.ts (Strict TypeScript types for autocomplete in React/Vue)
    • Tokens.swift and Colors.xml for native mobile targets.

When an engineer opens an IDE, autocomplete directly mirrors the naming in Figma:

/* In CSS: perfectly predictable */
.button-primary {
  background-color: var(--color-action-primary-bg);
  color: var(--color-action-primary-text);
  border-radius: var(--radius-interactive-md);
  padding: var(--space-4) var(--space-6);
}

.button-primary:hover {
  background-color: var(--color-action-primary-bg-hover);
}

Deprecation: how to retire a token without breaking production

Systems evolve. Eventually, you will need to rename or merge tokens. If you delete a token from your JSON file, you will break builds across multiple squads.

The professional way to deprecate tokens is aliasing with runtime telemetry:

/* Old token kept as a pointer to the new canonical token */
:root {
  --color-surface-panel: #FFFFFF; /* New canonical token */
  
  /* DEPRECATED in v2.4, to be removed in v3.0 */
  --color-bg-white: var(--color-surface-panel);
}

In your CSS build step or ESLint plugin, flag any usage of --color-bg-white as a build warning with a recommended codemod: "Warning: --color-bg-white is deprecated. Run `npx design-system-codemod` to migrate to --color-surface-panel."

The litmus test

A design token convention isn't successful because it looks elegant on a presentation slide. It is successful when a newly hired engineer can build an entire multi-step fintech checkout form, choose colors, borders, and spacing purely from IDE autocomplete, and pass visual review on the first try without a designer asking: "Hey, what hex code did you use here?"
