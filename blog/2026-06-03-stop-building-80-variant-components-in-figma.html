Stop building 80-variant components in Figma

Why exponential variant matrices bloat your library, cause canvas lag, and destroy overrides — and the slot and composition pattern that keeps components fast and maintainable.

Every design systems team reaches a tipping point where their Figma library turns into molasses. Designers click on a simple modal or button, wait three seconds for the properties panel to load, and complain that switching from "Default" to "Hover" wiped out the custom label they just typed.

When you inspect the master component, you discover the culprit: an eighty-variant monstrosity attempting to represent every conceivable combination of icons, sizes, states, and content configurations in a single component set.

The solution is not to build better variant matrices. It is to stop using variants for layout permutations and embrace composition and slots.

The math of variant explosion

Variants multiply exponentially. When you try to account for every layout option using variant properties, the combinatorial math quickly spirals out of control:

Size (3) × Style (4) × State (4) × HasIconLeft (2) × HasIconRight (2) × IsLoading (2)
= 384 individual component frames

In Figma's memory model, every variant frame is an active node tree with its own autolayout calculations, vector fills, and text layers. Multiply 384 frames across twenty components, and you have over 7,000 hidden nodes loading into memory every time a designer opens a working file. This is what causes Figma canvas lag and WebGL context crashes.

The golden rule: layer name matching

Have you ever changed an instance's variant property in Figma and watched your custom text revert back to "Button"? That is not a random bug — it is an architecture flaw in your component set.

Figma preserves user overrides across variant switches using one strict rule: the layer hierarchy and the layer name must match exactly across all variant frames.

  • If variant State=Default has a text layer named Label, but variant State=Hover has that same text layer named Text, Figma sees them as two unrelated objects. When the designer switches to Hover, Figma discards the typed text and renders the default value.
  • If you wrap an icon in an extra autolayout frame in only one variant, the layer depth diverges, and color overrides collapse.

The rule: Keep layer structures completely identical across all states. Never rename an inner layer in one variant without updating all sister variants.

The Slot pattern: composition over configuration

In frontend engineering (React, Vue, Web Components), developers don't build twenty modal variants. They build one modal shell with a children slot:

<Modal title="Export Data">
  <ExportForm /> {/* Swappable Slot Content */}
</Modal>

You can do the exact same thing in Figma using Instance Swap properties on placeholder slot components:

  1. Create a generic Slot placeholder: A simple autolayout frame with a subtle dashed outline, labeled _Slot / Placeholder (prefixed with an underscore so it isn't published in the team library).
  2. Embed the slot in your container: In your Master Modal or Card component, place an instance of the _Slot component where dynamic content lives.
  3. Expose an Instance Swap property: Bind that slot instance to an Instance Swap property named Content.
  4. Swap in consumer files: In production files, designers design their local form, table, or confirmation message as a local component, and swap it into the Modal's Content slot with one click.

Instead of 50 modal variants in your system library, you maintain one. Designers get infinite layout freedom, and nobody ever has to detach an instance.

When to use Variants vs. Component Properties

Before adding a new variant axis, use this checklist to choose the lightest tool for the job:

  • Variants: Strictly for mutually exclusive visual states that alter typography, surface fills, or core geometry (e.g. State: Default | Hover | Pressed | Disabled, or Variant: Primary | Secondary | Danger).
  • Boolean Properties: For showing or hiding sub-elements without duplicating frames (e.g. showIconLeft: true/false, showBadge: true/false).
  • Instance Swap Properties: For swappable content that has identical layout bounds (e.g. icons, avatars, and <Slot> placeholders).
  • Text Properties: For exposing text fields directly in the top-level property panel without drilling through nested layers.

Embracing slots and properties cuts your component set sizes by 70% to 80%. Your design library opens instantly, overrides stay locked in place, and your Figma structure mirrors the exact mental model your engineering team writes in code.
